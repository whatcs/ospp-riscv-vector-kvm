# M1 实现路线与代码落点对照

日期：2026-10-18  
源码基线：Linux `24a19b953e2a3d0ea5a8c4951a0ab8f32720c907`

## 1. 先把目标说清楚

Vector 硬件寄存器可以想成一块“每个 hart 只有一份的工作台”。Host 用户任务、Guest vCPU
和内核 Vector 都会轮流使用它。内存里的 `vstate` 是备份，硬件寄存器是正在工作的副本。

本项目要减少的不是所有 restore，而是下面这类重复搬运：

1. Guest A 已经把 Vector 数据留在 hart 0 的硬件寄存器；
2. 中间没有任何人覆盖这些寄存器；
3. Guest A 又在 hart 0 运行；
4. 内核却仍从内存把同一份数据全部加载一次。

要跳过第 4 步，必须同时证明“还是 A”“仍在 hart 0”“数据没有被覆盖”“A 的内存状态没有
被 reset/set-reg 改过”。只记录一个 `owner = A` 指针不足以表达这些条件。

## 2. 当前源码实际做了什么

### 2.1 vCPU load

`arch/riscv/kvm/vcpu.c:kvm_arch_vcpu_load()` 当前顺序是：

1. 保存 Host FP；
2. 请求恢复 Guest FP；
3. `get_cpu_vector_context()`；
4. `kvm_riscv_vcpu_host_vector_save()`；
5. `kvm_riscv_vcpu_guest_vector_restore()` 只设置 `RISCV_V_VCPU_NEED_RESTORE`；
6. `put_cpu_vector_context()`。

真正的 Guest Vector restore 被推迟到了 `kvm_riscv_vcpu_enter_exit()` 中、最终进入 Guest
之前。这说明官网要求中的“推迟到最后安全时刻”，主线其实已经完成了第一半；本项目新增
价值主要是安全地判断何时可以不做完整数据 restore。

### 2.2 vCPU put

`arch/riscv/kvm/vcpu.c:kvm_arch_vcpu_put()` 当前顺序是：

1. 保存 Guest Vector（仅 Guest VS=Dirty 时真正保存）；
2. 恢复 Host Vector；
3. 清 `RISCV_V_VCPU_CTX` 和 `RISCV_V_VCPU_NEED_RESTORE`。

因此 put 返回后，硬件 owner 按语义必须是 Host/无 owner，而不是 Guest。这里也是最初
“put 后 owner 到底清不清”的答案：按当前实现必须清；若不清，元数据会和硬件事实矛盾。

### 2.3 普通调度和内核 Vector

- `arch/riscv/include/asm/vector.h:__switch_to_vector()` 保存前一 task，给下一 task 设置延迟恢复；
- `arch/riscv/include/asm/entry-common.h:arch_exit_to_user_mode_prepare()` 在返回用户态前恢复；
- `arch/riscv/kernel/vector.c:riscv_v_first_use_handler()` 处理用户第一次执行 Vector 指令；
- `arch/riscv/kernel/kernel_mode_vector.c:kernel_vector_begin()` 在内核使用 Vector 前 flush 当前上下文；
- KVM 的 flush callback 依赖 `RISCV_V_VCPU_CTX` 和当前 CPU 的 `kvm_running_vcpu`。

但 `virt/kvm/kvm_main.c:kvm_sched_out()` 在 `kvm_arch_vcpu_put()` 之后会把
`kvm_running_vcpu` 清成 NULL。这是“只在 KVM 内保留一个跨 put owner”的主要断点。

## 3. 路线 A：KVM-only 窄方案

### 3.1 方案

只修改 `arch/riscv/kvm/`：在 KVM 内增加 per-hart owner；load 时若 owner 仍是当前 vCPU，
跳过完整 restore。

### 3.2 为什么原形态不能直接实现

如果 put 仍恢复 Host，Guest 已被覆盖，owner 不可能继续有效；如果 put 不恢复 Host，普通
task、首次使用、kernel Vector、hotplug/PM 又看不到 KVM 私有 owner。跨调度保留
`RISCV_V_VCPU_CTX` 也不成立，因为 `kvm_running_vcpu` 随 sched-out 被清空，现有 callback
可能得到 NULL。

所以纯 KVM-only 只能有两种结果：

- 每次 put 都清 owner：安全，但下次 load 永远没有跨 put 命中，几乎没有新增收益；
- put 后不清 owner：可能命中，但通用覆盖路径不闭环，不安全。

### 3.3 结论

路线 A 可以用来做观测和对照，不能作为当前行为优化方案。除非后续证明优化窗口完全位于
一次 `vcpu_load` 和 `vcpu_put` 之间；但当前该区间内的普通 VM-exit/re-entry 本来就不会重复
restore，因此没有明显可优化对象。

## 4. 路线 B：通用 RISC-V Vector 交接 hook

### 4.1 核心思路

put 时仍把 Guest 完整保存到内存，使内存始终是最新的；若能够证明 Host 没有 Vector 恢复
义务，则暂不把 Host 数据加载回硬件，把硬件标成：

```text
owner = Guest A
data_registers = resident（仍在）
control_csrs = invalid（save 中的 vsetvli 已经改过）
memory = fresh（已经完整保存）
```

之后：

- 同一 vCPU、同一 hart、generation 未变且无人覆盖：只恢复 Guest 控制 CSR；
- 任何其他使用者要覆盖 Vector：先把残留 owner 失效，再正常 restore/初始化；
- 因为 Guest 内存已经是最新，失效时不需要再解引用 vCPU 并保存一次。

这比“硬件完整有效/无效”二值模型多一个 `DATA_RESIDENT` 状态，正好对应当前 save 会保留
v0-v31 数据、却改写 `vl/vtype` 的事实。

### 4.2 为什么必须有通用 hook

残留 Guest 可能在 KVM 已经不处于 running 状态时存在。下列路径都可能成为下一位 Vector
使用者，必须在覆盖前看到并清除残留标记：

| 路径 | 候选落点 | 作用 |
|---|---|---|
| 普通 task 延迟恢复 | `riscv_v_vstate_restore()` 或其统一下层 | restore 前失效 Guest 残留 |
| 用户首次使用 | `riscv_v_first_use_handler()`/统一恢复入口 | 初始化或返回用户态前失效 |
| kernel Vector | `__riscv_flush_vector_context()` | kernel 覆盖前失效 |
| task switch | `__switch_to_vector()` | 处理调度期已经开启/保存 Vector 的情况 |
| CPU offline/PM | RISC-V CPU 生命周期回调 | 清本 hart 的 owner |

理想实现不是在五处复制 KVM 判断，而是提供一个很小的通用接口，例如“当前 hart 是否有
外部残留 owner；如有则令其失效”。具体 API 名称要在原型评审时决定。

### 4.3 生命周期要求

per-hart 缓存不能依赖一个可能已经 free 的 vCPU 指针。M1 至少需要：

- identity：可比较但失效路径不解引用；
- generation/cookie：reset、set-reg、destroy 后即使地址被复用也不能误命中；
- CPU-local 更新规则：在禁抢占/关中断的正确上下文中读写；
- module unload：hook 注销后先经过 RCU 同步，并清理所有 hart 的残留元数据；
- hotplug/PM：CPU 下线或丢失硬件状态时清 owner。

## 5. 一个仍未证明的关键前提

P1 两个受控窗口中，restore request 处的 Host VS 100% 为 Off。这说明优化窗口看起来很大，
但不能仅凭这一个采样字段就删除 `host_vector_save/restore`。源码特意注明 Host `sstatus`
可能在别处被修改，因此需要先证明：

> 在所有 load/put、抢占、kernel Vector 和用户返回交错中，Host VS=Off 是否真的等价于
> “没有必须恢复的 Host 硬件 Vector 内容”。

在这个证明完成前，路线 B 只能做影子判定，不能改变行为。

## 6. M1 的实际拆分

### M1-0：shadow owner（下一代码步骤，不改变行为）

增加 trace/统计状态，模拟未来 owner：

- put 时记录候选 `DATA_RESIDENT` 以及当时 Host VS；
- load 时记录同 vCPU/同 hart/generation 是否候选命中；
- kernel Vector、其他 vCPU、迁移、reset/set-reg/destroy 等只记录失效原因；
- 所有真实 save/restore 保持原样。

这个阶段回答“快路径理论上能命中多少次”和“主要被谁打断”，不会引入状态污染。

### M1-1：通用失效接口骨架

在行为仍关闭的情况下接通通用覆盖路径，加入断言和 trace，证明不会漏掉覆盖者。

### M1-2：控制 CSR-only restore

把 `__vstate_csr_restore()` 所需能力封装为明确的内部接口，单独测试 `vstart/vl/vtype/vcsr`
和 v0-v31 数据均正确。

### M1-3：小范围启用

仅对 G1 已证明安全的 Host VS=Off、同 hart、同 vCPU、同 generation 场景启用；其他情况
全部回退到现有完整 restore。

## 7. 对 GET/SET、reset 和 destroy 的处理

M1 保持“put 后 Guest 内存最新”，因此：

- GET 可直接读内存，但需要使 shadow/真实缓存语义保持一致；
- SET 写入后必须递增 generation，使任意 hart 上的旧残留不能命中；
- reset 同样递增 generation；
- destroy 必须先使所有可能引用该 identity 的缓存失效，再释放 Vector buffer；
- 跨 hart load 天然不能命中原 hart 的硬件数据，并应记录 migration invalidation。

若以后进一步优化到“不在 put 保存 Guest”，GET 就必须先触发同步；这不属于 M1。

## 8. 当前决定

1. 否决“直接实现 KVM-only 跨 put 快路径”；
2. 采用路线 B 作为候选方向，但先做 M1-0 shadow 观测；
3. M1 继续保持 Guest 内存新鲜，不优化 save，只尝试减少可证明冗余的 full restore；
4. G1 未通过前不改变行为；
5. QEMU 只验证正确性和事件次数，性能结论留给真实硬件。

这个决定保留了官网要求中的 per-hart owner 和延迟恢复方向，同时修正了申请书/旧计划中
“一个 owner 指针就足以跨 put 命中”的不完整部分。
