## 3. 对 dsh 初版计划的源码修正

### 3.1 已过时的前提

初版计划把环境视为硬阻塞项。现在 L1/L2、KVM、RVV、SSH 和两套内核配置均已验证，
环境不再是主线任务；以后只做回归维护。

### 3.2 不能直接照做的 P2～P4

初版路线大体是“增加 per-CPU owner → 命中时跳过 restore”。源码表明它还缺一层闭环：

1. `kvm_arch_vcpu_put()` 先保存 Guest，再恢复 Host。恢复 Host 后硬件里已经不是 Guest，
   所以此时不能继续声称 Guest 是硬件 owner。
2. 如果为了保留 Guest 而跳过 Host restore，通用调度、用户 Vector 首次使用、
   `kernel_vector_begin()`、CPU hotplug/PM 等路径必须能发现并失效这份残留状态。
3. `RISCV_V_VCPU_CTX` 属于 `current->thread.riscv_v_flags`，而 `kvm_sched_out()` 在 arch put
   后会清除 `kvm_running_vcpu`。跨 put 生硬保留该标志会使现有 flush callback 找不到 vCPU。
4. `__riscv_v_vstate_save()` 会用 `vsetvli` 改写 `vl/vtype`，因此“数据寄存器仍在”不等于
   “完整 Guest Vector 状态可直接进入”；至少需要恢复控制 CSR。

结论：P2～P4 改成“先影子统计、再接口闭环、最后启用行为”的三段式，不直接上线快路径。

### 3.3 代码范围不能预先限制在 `arch/riscv/kvm/`

初版 E5 把 KVM-only 当成固定决定。源码表明，只要缓存要跨 `vcpu_put/load` 存活，通用
RISC-V Vector 路径就必须至少有一个“覆盖硬件前先让残留 owner 失效”的接口。因此：

- “尽量少改通用代码”仍是偏好；
- “绝不改 `arch/riscv/kernel/` 或 `arch/riscv/include/asm/`”不再是成立的设计约束；
- 是否引入通用 hook 必须由影子统计和失效边界试验证明。

### 3.4 `GET_ONE_REG` 也是同步边界

如果未来允许硬件 Guest 状态比 `guest_context.vector` 更新，那么：

- `SET_ONE_REG` 写内存前必须使硬件缓存失效；
- `GET_ONE_REG` 读内存前必须先把最新硬件状态同步回内存；
- reset/destroy/迁移同样不能只改内存或释放对象。

M1 的保守约束是：每次 put 仍完整保存 Guest，始终保持 Guest 内存为最新。这样先避免
把 GET 路径也卷入第一版优化。

M1C 运行验证进一步确认：GET 后同 hart owner 仍可命中并执行 CSR-only；SET 会推进
generation，使下一次 load 以 `reason=generation` 回退 full restore。

### 3.5 QEMU 的用途

嵌套 QEMU/KVM 环境适合验证功能、事件次数、污染和失效规则；它的耗时不能作为真实硬件
性能结论。最终性能收益需要真实 RISC-V Vector 硬件，若暂时没有则明确标注“待补测”。

### R2：M1 最小行为优化

- 仅在明确证明 Host 没有 Vector 恢复义务时，允许硬件数据寄存器保留 Guest；
- per-hart 缓存保存不可误解引用的 identity + generation + 有效性状态；
- 任意通用 Vector 使用者覆盖寄存器前，先使缓存失效；
- 同 hart、同 vCPU、generation 未变且未发生失效时，只恢复必要控制状态；
- 默认关闭或用 static key/配置隔离，便于 A/B 与回退。
