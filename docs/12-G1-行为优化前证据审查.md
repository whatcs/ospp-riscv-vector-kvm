# G1 行为优化前证据审查

日期：2026-10-19  
源码基线：Linux `24a19b953e2a3d0ea5a8c4951a0ab8f32720c907`  
前置工作：C1 + P1 + M1A + M1B

## 1. 这一关要回答什么

M1B 证明了“很多 put/load 之间，Guest 数据寄存器事实上还留在同一 hart”。但统计命中不等于
可以直接删掉 restore。真正改行为前，必须同时证明三件事：

1. 不恢复 Host 不会丢掉 Host 自己的 Vector 状态；
2. 留在硬件里的 Guest 数据没有被任何别的使用者覆盖；
3. 即使数据寄存器仍正确，被 save 指令改写过的 `vstart/vl/vtype/vcsr` 也会恢复。

可以把它理解为：M1B 只确认“书还在这张桌上”；G1 还要确认“没人换过书，而且书签也放回了
正确页”。

## 2. `Host VS=Off` 能证明什么

KVM 读的是 `task_pt_regs(current)->status & SR_VS`，即进入内核时保存下来的 QEMU vCPU
线程用户态 VS，而不是此刻硬件 `sstatus.VS`。

- `Host VS != Off`：Host 用户态存在 Vector 状态义务，必须走原有完整 Host save/restore；
- `Host VS == Off`：该用户态上下文没有需要恢复的 Vector 状态，可以不保存或恢复
  `host_context.vector`；
- 不能拿当前硬件 `sstatus.VS` 做相同推断，因为内核代码、KVM save/restore 本身都会临时修改它。

这个结论只允许“Host VS Off + shadow 精确命中”进入快路径。它不是说硬件此时一定空闲；硬件
里可以保留 Guest 数据，正是 owner 协议需要表达的事实。

## 3. 谁会覆盖硬件 Vector，M1B 如何拦住

| 覆盖者/入口 | 覆盖前动作 | 对残留 Guest 的处理 |
|---|---|---|
| 普通 task save | `riscv_v_vstate_save()` | `task_save` 失效 |
| 普通 task restore，包括延迟恢复 | `riscv_v_vstate_restore()` | `task_restore` 失效 |
| syscall/首次使用等 discard | `riscv_v_vstate_discard()` | `task_discard` 失效 |
| 非抢占 kernel Vector | `kernel_vector_begin()` → flush | `kernel_vector` 失效 |
| 抢占式 kernel Vector 外层开始 | `riscv_v_start_kernel_context()` → flush | `kernel_vector` 失效 |
| 抢占式 kernel Vector 内层嵌套 | 直接低层 save/restore | 外层开始时已经失效，不会再有有效 KVM owner |
| CPU offline / non-retention PM | `kvm_riscv_csr_cleanup()` | `cpu_state` 失效 |

用户首次使用 Vector 时，VS 原先为 Off，非法指令处理会分配零上下文并设置延迟恢复；真正返回
用户态前仍经过 `riscv_v_vstate_restore()`，所以会在覆盖硬件前失效 owner。signal 和 ptrace
读取当前任务状态时若需要实际 save，也走同一个带失效通知的 wrapper。

上述证明的边界是：内核 Vector 使用者必须遵守现有 `kernel_vector_begin/end` 接口。绕开内核
API 直接写物理 Vector 寄存器，本来就会破坏普通任务上下文，不是该优化单独引入的假设。

## 4. 为什么仍需 CSR-only restore

`__riscv_v_vstate_save()` 先把 Guest 的 `vstart/vl/vtype/vcsr` 保存到内存，再用 `vsetvli`
切到便于整组保存寄存器的配置。数据寄存器保存后仍含 Guest 数据，但 `vl/vtype` 等控制状态已
被保存过程改写。

所以命中时不能“什么都不做”直接进 Guest。最小安全动作是：

```text
恢复 vstart + vl + vtype + vcsr
不重新加载 v0..v31
```

现有 `__vstate_csr_restore()` 已实现这组控制 CSR 的恢复，原型可以复用它，而不另写汇编。

## 5. 多 hart、管理接口与生命周期

- dirty Guest 每次真正保存回内存后递增 generation；因此 vCPU 在另一个 hart 修改过状态后，
  原 hart 的旧 owner 一定 generation mismatch；
- reset 和 `KVM_SET_ONE_REG` 也递增 generation；
- M1 第一版 put 仍完整保存 Guest，所以 `KVM_GET_ONE_REG` 总能读到最新内存，不需额外同步；
- owner 中保存的 vCPU 指针只比较、不解引用；对象地址若被复用，单调 cookie 阻止 ABA 假命中；
- CPU hotplug/PM 清本 hart owner，模块卸载先注销 RCU callback。

CPU6→CPU7→CPU6 定向实验已经实际观察到 `reason=generation` 和随后的 full restore，而不是只
依靠代码推断。

## 6. M1C 原型的安全协议

原型默认关闭，关闭时必须与 M1B 行为完全相同。打开后只允许下面一条窄路径：

1. put 仍完整保存 dirty Guest，保持内存始终最新；
2. 只有 Guest 确实 resident、Host VS Off 时，put 才跳过 Host Vector restore，并发布 owner；
3. load 只有同 hart、同 vCPU、同 cookie、同 generation 且未失效才命中；
4. 命中时跳过 Host save 和 Guest 数据寄存器 restore，只安排 CSR-only restore；
5. load 后到真正 Guest entry 前，若普通 task restore、kernel Vector 等任一通用 Vector
   失效路径介入，必须把 CSR-only 请求升级成 full restore；
6. 任一条件不满足都走当前完整 save/restore 路径；关闭参数即可回退。

第 5 点是源码审查新发现的竞态：shadow load 会先消费 owner，Guest 尚未 entry 时硬件数据仍可能
被其他 Vector 使用者覆盖。仅有 M1B 的 per-hart owner 失效已不够，pending CSR-only 标志
也必须被统一的 `riscv_v_owner_invalidate()` 回调识别并升级。

## 7. 原型出口判据

原型至少要同时通过：

1. 默认关闭时 full restore 数与 M1B 一致，确认无行为变化；
2. 打开后稳定 RVV 出现 CSR-only restore，full restore 显著减少；
3. 同 hart Host RVV 干扰后回退 full restore，Host/L2 数据均正确；
4. CPU6→CPU7→CPU6 在 Guest 被修改时发生 generation miss；
5. load 后、Guest entry 前的 kernel Vector 干扰能把 CSR-only 升级为 full restore；
6. CPU hotplug、reset、get/set-reg 与 V=y/V=n 构建无回归；
7. `git diff --check` 和严格 checkpatch 通过。

QEMU 嵌套环境只用来证明状态机、事件计数和正确性；真实加速收益仍需 RISC-V 硬件测量。
