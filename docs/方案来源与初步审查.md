## 已确认的设计缺口

### 1. 跨 vcpu_put/load 保留 guest 内容的收益路径尚不成立

`arch/riscv/kvm/vcpu_vector.c:71-76` 中，host restore 的条件为
`!kvm_riscv_isa_check_host(V)`。`arch/riscv/kvm/isa.c:115-145` 说明该检查成功返回 0，
所以 host 支持 V 时会实际调用 `__kvm_riscv_vector_restore()`。这里的 `!` 不是“host 不支持 V”。

`vcpu.c:674-678` 在 put 时保存 guest，再恢复 host。若按草案 F-1 清 owner，则下次 load 不会命中；
若强留 owner，则它已经与硬件内容不符。仅增添一个 owner 指针无法解决这个矛盾。
后续须证明能在哪个安全边界保留 guest，可能涉及调整 KVM 内 host restore 策略。
目前不修改这部分运行时逻辑。

### 2. 同一次 KVM_RUN 内的轻量 exit/entry，已有延迟恢复机制会跳过未被要求的 restore

`vcpu.c:822-827` 只在 NEED_RESTORE 置位时恢复，并立即清该标志。
`kvm_arch_vcpu_ioctl_run()` 的循环并不是每次 guest exit 都调用一遍 vcpu_put/load。
因此“频繁退出”不自动等于“当前频繁全量恢复”。S-1 需要区分内核内处理退出、返回 userspace
处理退出和调度引起的 put/load，并先计数，再判断新增优化是否有收益。

### 3. 向量数据未变，不代表完整上下文未变

`arch/riscv/include/asm/vector.h:203-237` 的保存函数先保存控制寄存器，随后用
`vsetvli ... e8,m8` 改写硬件 vl/vtype 以保存 v0～v31。故“只保存、不覆盖向量数据”
仍不能推出“可以跳过整个恢复”。有效性模型须覆盖 vl、vtype、vstart、vcsr 等控制状态。

### 4. 跳过恢复仍须维护 KVM 的上下文标志

host restore 会清除 RISCV_V_VCPU_CTX 和 NEED_RESTORE。现有 entry 在真正恢复时重新设置 CTX。
申请书示意代码在 owner 命中时直接 return，若将来跨 put/load 保留 owner，不能原样套用：
仍须保证 CTX 等状态正确，否则 kernel-mode Vector 的 flush 回调会走错上下文。

此外，flush_vector 在 guest 已 Clean 时要求恢复，不必然是冗余：内核随后可能覆盖寄存器。
原计划中把 Clean 条件直接当作“次要冗余来源”的说法需要撤回为待证假设。

## 可行性判断

- 项目方向合理，ARM64 提供了成熟的设计参照；现有 H+V 模拟环境允许开展功能实验。
- 具体草案尚不是可直接实现并保证收益的方案，需要先修正上述矛盾。
- 当前不能承诺固定比例的收益、任意负载加速或上游合并。
- 后续先用事件计数证明哪里有冗余，再设计有效性边界；污染测试必须同时覆盖向量数据和控制状态。
- C/A 环境工作独立有价值，可继续推进。B 与优化实现待用户继续学习和讨论后开展。
