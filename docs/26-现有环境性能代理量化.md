# 现有环境下的性能代理量化与发布口径

日期：2026-10-30

## 1. 结论

现有环境值得做、也已经能够完成的是**性能代理量化**：验证快路径实际减少了多少次完整
Vector 恢复，以及因此少执行了多少架构状态装入。它可以证明优化机制有效、工作量显著下降。

现有环境不适合报告纳秒、周期数或端到端加速比。原因不是 L2 没有使用 KVM，而是执行
RISC-V KVM 内核代码的 L1 本身运行在 x86 宿主机上的 QEMU TCG 中；该代码最终仍由 TCG
翻译执行，并不在真实 RISC-V Vector 处理器上原生执行。因此本文只报告正确性、事件次数和
架构状态量，不把 TCG 时间换算为真机性能。

当前 RFC v0 已经发出。本文先作为项目证据和下一版材料保存，**不单独追发一封性能邮件**。
继续等待维护者回复；若维护者询问性能，则说明环境限制并提供这里的事件量化；若形成 RFC v1
或正式 PATCH v1，再把合适的结论写入 cover letter/changelog。只有获得真机或维护者明确要求
时，才补真实耗时基准。

## 2. 测试环境为什么只能做代理量化

当前链路为：

```text
Windows/x86 物理机
  └─ VMware x86 Ubuntu
       └─ QEMU TCG：RISC-V L1，H+V，VLEN=256
            └─ L1 内 QEMU -accel kvm：RISC-V L2
```

可复现配置见：

- `lab/start-l1.sh`：`-accel tcg -cpu rv64,h=true,v=true,vlen=256`；
- `lab/start-l2.sh`：`-accel kvm -cpu host`；
- `lab/README.md`：记录三层资源与版本。

L2 的 guest entry/exit 确实走 L1 KVM，但 L1 内核中的 RISC-V 指令仍由外层 TCG 翻译。
QEMU 官方文档也明确指出，TCG 的指令计数不是周期精确的模拟：
<https://qemu.readthedocs.io/en/v7.2.19/devel/tcg-icount.html>。

所以当前环境可以可信回答“某条代码路径发生了多少次”“状态是否正确”，不能可信回答
“真实 RISC-V 芯片上节省了多少周期或纳秒”。

这组是对实际投稿代码的确认性冒烟，不冒充新的严格 A/B；它证明 RFC v0 版本仍实际进入
CSR-only 路径。严格事件比例继续以上述 30+30 受控窗口为主。

两个窗口的调度和恢复事件总数不完全相同，因此它们不是逐事件配对实验；不能假设关闭组的
每个 restore 都与开启组某个 restore 一一对应。但在相同固定次数的功能负载下，full restore
从 2194 降到 6，事件计数减少：

```text
(2194 - 6) / 2194 = 99.7265%
```

这个百分比的准确名称是“完整恢复事件减少比例”，不是运行时间加速比。

## 4. 架构状态工作量量化

当前配置 `VLEN=256 bit`，所以每个 Vector 寄存器宽度为：

```text
VLENB = 256 / 8 = 32 bytes
```

RISC-V 有 `v0..v31` 共 32 个 Vector 数据寄存器。一次 full restore 需要恢复的数据寄存器
架构状态量为：

```text
32 registers * 32 bytes = 1024 bytes
```

开启组直接观测到 1948 次 CSR-only restore。每一次都恢复控制 CSR，但跳过 `v0..v31` 的
重新装入。因此仅在该开启组采样窗口中，可以直接归因的、无需再次装入的数据寄存器状态为：

```text
1948 * 1024 = 1,994,752 bytes = 1,948 KiB = 1.90234375 MiB
```

这表示“没有执行的架构寄存器状态装入量”，不是精确的 DRAM/缓存流量：实际数据可能来自
缓存，指令实现和微架构也会影响真实成本。它同样不能直接换算成周期、纳秒或应用吞吐量。

## 5. 为什么不在当前环境强测耗时

1. `__kvm_riscv_vector_restore()` 与 CSR-only helper 是 `static __always_inline`，不是可稳定单独
   挂 function-graph filter 的普通函数；
2. 真正的恢复位于 `noinstr kvm_riscv_vcpu_enter_exit()` 的静默区，在其中随意加入普通
   tracepoint 或 `ktime_get()` 不满足当前上下文约束，还会改变被测路径；
3. 现有 `restore_request` 与 `restore` tracepoint 没有紧贴 helper 的入口和出口，二者时间差
   会混入 guest 执行、VM exit 等工作，不能解释为 restore latency；
4. 即使专门增加可用的计时插桩，当前测到的仍是 TCG 翻译环境的时间，不是真实 RISC-V
   Vector 硬件代价。

所以现在为获得一个看似精确的纳秒数字而改内核，成本高、干扰大、结论弱，反而容易误导。

## 6. 若以后获得真机，怎样补正式性能测试

在支持 H 扩展和 Vector 的真实 RISC-V 平台上，固定内核基线、配置、VLEN、CPU 频率策略和
vCPU 绑核，比较至少三组：未应用补丁、应用补丁但快路径关闭、应用补丁且快路径开启。

使用反复 KVM_RUN/退出并保持同一 vCPU 驻留机会的负载，分别进行：

- 不开 trace 的计时轮次，报告多次运行的中位数与离散程度；
- 单独的 trace/计数轮次，确认 full 与 CSR-only 路径比例；
- RVV 状态校验和 Host/Guest 干扰回归，确保性能结果没有以正确性为代价。

可报告 wall time、每次 KVM_RUN 延迟、cycles/instructions，以及 full/CSR-only 事件数。计时和
trace 应分轮运行，避免把追踪开销混入主要性能数字。
